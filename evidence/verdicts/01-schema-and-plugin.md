## C6 — one inaccurate claim in PROGRESS.md

**The COALESCE-in-generated-column line is wrong as written.** PROGRESS.md says:

> `COALESCE(ct, CAST('9999-12-31 23:59:59' AS DATETIME))` in a generated column — **rejected** with "Function or expression … cannot be used in the GENERATED ALWAYS AS clause"

That is not what MariaDB 11.4 does. The `CREATE TABLE` is **accepted**, the column is created, and it computes correct values:

```
CREATE TABLE g1(ct DATETIME(6) NULL, m DATETIME(6) GENERATED ALWAYS AS (COALESCE(ct, CAST('9999-12-31 23:59:59' AS DATETIME))));
[ACCEPTED]
ct=NULL                      -> m=9999-12-31 23:59:59.000000
ct=2026-02-02 03:04:05.000000 -> m=2026-02-02 03:04:05.000000
```

The rejection happens only when you try to **index** it:

```
CREATE INDEX i_g1 ON g1(m DESC);
ERROR 1901 (HY000): Function or expression 'coalesce(`ct`,cast('9999-12-31 23:59:59' as datetime))'
cannot be used in the GENERATED ALWAYS AS clause of `m`
```

So the quoted error is real and the engineering conclusion (drop the inner CAST to get an indexable column) is correct and confirmed — but the line attributes the rejection to the wrong operation. It should say the column is accepted and only the index on it is rejected. Per the repo's own "wording matches evidence" rule, worth a one-line correction.

**The other surprising probe lines all check out**, each `[REJECTED]` with ERROR 1064 syntax errors: `->`, `->>`, `CAST(x AS JSON)`, `x MEMBER OF (...)`, expression indexes, multi-valued `CAST(col AS CHAR(255) ARRAY)` indexes. And `JSON_VALUE('{"b":true}','$.b')` returns `1` with `= 'true'` yielding **0**, while `JSON_UNQUOTE(JSON_EXTRACT(...))` returns `true` with `= 'true'` yielding **1** — exactly as documented. The "accepted unchanged" list also verified: FULLTEXT `MATCH … AGAINST` on the STORED generated `Text01` correctly matched only the 'quick brown fox' row, and `ON DUPLICATE KEY UPDATE … VALUES(col)` upserted and recomputed the generated columns.

**Claims that survived independent checking:**
- "11 indexes dropped" — exactly 11 (73 MySQL vs 62 MariaDB), and the 11 names match the schema header list one-for-one, with zero indexes present only in MariaDB.
- No search attribute is silently lost: column parity is exact across all three visibility tables; MariaDB adds only `close_time_or_max`.
- `schema/mariadb/v11/visibility/schema.sql` is identical to `versioned/v1.0/schema.sql`, so a fresh install and a migrated install agree.

**Minor, non-blocking:** PROGRESS.md's Notes list `cmd/server/main.go` and `cmd/tools/sql/main.go` as "plugin registration sites to touch", but neither is in the diff and neither needs to be — registration happens via `init()` in `mariadb.go` inside the existing `sqlplugin/mysql` package. That's a plan-time note rather than a completion claim, so it's not an overclaim, but it will read as a gap to the next session.
